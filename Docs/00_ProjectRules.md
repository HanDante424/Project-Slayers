# Project Slayers - Project Development Rules

상태: 현재 활성 개발 기준  
용도: Codex 및 개발 작업에서 공통으로 참조하는 프로젝트 운영·구조 기준

---

## 1. 문서의 역할

이 문서는 Project Slayers 저장소에서 사용하는 개발 규칙의 기준 문서다.

- `AGENTS.md`는 Codex의 작업 행동 규칙을 정의한다.
- 본 문서는 Project Slayers의 실제 개발 원칙과 구현 방향을 정의한다.
- 세부 시스템은 `Docs/01` 이후 문서를 우선한다.
- 게임 디자인·밸런스·세계관·캐릭터 설정이 필요한 경우 관련 문서가 없으면 임의로 확정하지 않는다.

---

## 2. 소스 우선순위

설정이나 설계가 서로 충돌할 경우 다음 우선순위를 적용한다.

1. 사용자가 이후 직접 확정한 최신 내용
2. 최신 `[ACTIVE UPDATE]`
3. `[CONFIRMED]`
4. 아직 폐기되지 않은 보존 원문
5. 시각 항목에서는 Primary Canon 원본 자산
6. `[CHECK]`, `[TEMP]`, 프로토타입, 보류 항목

규칙:

- `[CHECK]`, `[TEMP]`, 프로토타입, 보류 상태는 임의로 확정하지 않는다.
- `[DEPRECATED]`는 최신 활성 정의보다 우선하지 않는다.
- 충돌이 해소되지 않으면 구현 전에 충돌 내용을 보고한다.
- 코드에 이미 존재한다는 이유만으로 그것을 최신 게임 디자인으로 확정하지 않는다.

---

## 3. 현재 프로젝트의 위치

Project Slayers는 신규 Unity 2D 액션 게임 프로젝트다.

과거 프로토타입 두 종은 다음 목적의 참고 자료다.

- 사용자가 과거에 구현한 기능과 코드 습관 확인
- 구현 경험이 있는 기능의 개념 보존
- 실패한 구조를 반복하지 않기 위한 비교 자료

직접 계승하지 않는다.

특히 다음 구조는 신규 프로젝트의 기본 구조로 가져오지 않는다.

- 거대한 중앙 Manager
- 숫자 ID 기반 대형 switch
- 배열 순서에 의존하는 스탯 의미
- `Transform.GetChild(index)`에 의존하는 중요한 UI 연결
- ScriptableObject 자체를 저장/런타임 상태처럼 직접 변경하는 구조
- Animator 상태 이름이 게임 상태의 원본이 되는 구조
- 스킬마다 bool 하나씩 추가하는 구조
- 스킬마다 전용 피해 MonoBehaviour를 만드는 구조
- 풀 종류마다 중복 구현하는 구조
- 정상 종료만 존재하고 강제 취소 정리가 없는 구조

---

## 4. 신규 개발 순서

현재 기준 신규 개발 순서는 다음과 같다.

1. 프로젝트 초기화
2. 기본 이동과 점프
3. 행동 상태와 이동 잠금
4. 범용 오브젝트 풀
5. 기본 공격과 훈련용 적
6. 행동 타임라인
7. 일반 스킬
8. 입력 버퍼와 캔슬
9. 다단 공격, 히트스톱, 무력화, 적 AI
10. 장비, 저장, 성장

이 순서는 절대적인 파일 생성 순서가 아니라 시스템 의존관계의 기본 기준이다.

---

## 5. 코드 구조 원칙

선호:

- 명시적 타입
- 필요한 곳에서 enum 사용
- 작은 책임 단위의 컴포넌트
- 명확한 소유권
- 데이터와 런타임 상태의 분리
- 캐릭터와 스킬 수가 늘어나도 수정 범위가 급격히 커지지 않는 구조
- Inspector에서 확인 가능한 참조와 기본 데이터
- 공통 기능의 재사용
- 명시적 생명주기와 정리 경로

지양:

- 전역 상태 남용
- 서로의 내부 필드를 직접 수정하는 강결합
- 기능 하나 추가할 때 여러 무관한 파일을 동시에 고쳐야 하는 구조
- 숫자 인덱스 자체가 의미가 되는 구조
- Unity 직렬화 참조를 고려하지 않은 무분별한 파일/필드 이름 변경
- 요청되지 않은 대규모 리팩터링

---

## 6. Animator 원칙

Animator는 출력 계층이다.

- 게임 상태를 결정하지 않는다.
- ActionController 또는 대응 게임플레이 컨트롤러가 행동 상태를 결정한다.
- Animator는 결정된 결과를 표현한다.
- 공격 가능 여부, 이동 가능 여부, 캔슬 가능 여부, 무적 여부, 액션 종료 여부를 Animator 상태 이름으로 판정하지 않는다.
- Animation Event는 프레임 기반 이벤트에 사용할 수 있으나, 정상 애니메이션 종료만을 정리 경로로 삼지 않는다.

---

## 7. Unity 직렬화 자산 원칙

다음 자산은 요청이 없는 한 임의로 수정하지 않는다.

- Scene
- Prefab
- Animator Controller
- Animation Clip
- ScriptableObject 데이터 에셋
- Input Action Asset
- Timeline
- ProjectSettings
- Package 설정
- Material / VFX 직렬화 에셋

직렬화 자산을 수정할 경우:

- 관련 없는 필드를 재저장하지 않는다.
- `.meta` GUID를 보존한다.
- UnityEvent 메서드 참조와 직렬화 필드 이름 변경에 주의한다.
- 생성/삭제/이동 파일을 최종 보고에 명시한다.

---

## 8. 검증 원칙

실제로 실행하지 않은 검증을 성공했다고 말하지 않는다.

구분:

- 소스 정적 검토
- diff 검토
- `git diff --check`
- 자동화 테스트
- Unity Editor 컴파일
- Player Build
- Play Mode
- 실제 게임플레이 검증
- Inspector 직렬화 참조 검증

예:

- Unity를 실행하지 않았으면 "Unity 컴파일 성공"이라고 하지 않는다.
- Player Build를 하지 않았으면 "빌드 성공"이라고 하지 않는다.
- Scene/Prefab/Animator 연결은 로컬 Unity 확인이 필요한 경우 명시한다.

---

## 9. Git 운용 기준

`main`은 안정 브랜치로 취급한다.

권장 작업 흐름:

1. 문제 분석
2. 수정 계획 제안
3. 별도 브랜치에서 수정
4. Commit
5. diff 확인
6. Unity에서 필요한 검증
7. `main`에 Merge
8. Push
9. 작업 브랜치 삭제

금지:

- 명시적 요청 없는 force-push
- 게시 이력 재작성
- 기존 사용자 변경 강제 폐기
- 미병합 작업이 있는 브랜치 삭제
- 목적 없는 대규모 포맷 변경

## 10. 현재 프로젝트 상태

[ACTIVE UPDATE 2026-10-31]

세부 구현 현황은 `Docs/08_CurrentStatus.md`를 기준으로 한다. 이 절은 요약이다.

구현되어 있는 기반:

- 이동 / 점프, 기본 입력, 키 바인딩
- 메뉴 / Town 패널
- 저장 / 로드 기초 (`GameData`만 해당, 인벤토리·장비는 미저장)
- 캐릭터 스탯: 레벨 성장 → Modifier → 최종 스탯, 현재 HP/MP 런타임 자원
- 인벤토리 · 대장간 제작 · 독립 장비 인스턴스 · 장착 · 세트 효과 (`06` 문서)
- 메이헴 캐릭터 전용 액션과 액션별 입력 버퍼 (`ActionInputBuffer`)
- 기본 피해 계산(공격력 × 계수 / 100), 적 피격 · 경직 · 넉백 · 사망
- 테스트용 고블린 이동/추적/공격, 고블린 전용 풀
- 스테이지 정의 데이터와 Town 스테이지 선택, 전투 결과 화면

아직 정식 공통 구현이 필요한 주요 영역:

- 공통 ActionController (현재는 캐릭터별 Mechanism이 액션을 직접 관리)
- 액션 단계(Startup/Active/Recovery)와 CancelPower / InterruptArmor 기반 캔슬
- 범용 풀
- 피해식의 크리티컬 · 속성 · 방어/저항 배율 (`02` 문서)
- 일반 스킬 시스템 (스킬 추가 시 입력·인터페이스를 개별 추가하는 현재 구조의 대체)
- 다단 공격 공통 처리, 히트스톱, 무력화
- 본격적인 적 AI
- 스테이지 진행(적 배치·웨이브·클리어 조건)과 보상 지급
- 인벤토리·장비의 디스크 저장

이 목록은 미구현 상태를 의미하며 Codex가 임의 설계해도 된다는 뜻이 아니다.
