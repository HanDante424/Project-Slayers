## 2. 세 채팅의 역할 정리

### 메인 메뉴 레이아웃 정리

- 실제 타운 UI 제작 이력을 담은 채팅이다.
- `TownMenuController`와 전투·캐릭터·상점·연구·창고·옵션 패널 연결이 정상 작동한 시점까지를 완료 기록으로 본다.
- 앞으로 기능 구현을 계속하는 주 작업 채팅으로 사용하지 않는다.

### 리모트 활용 비교

- Git 도입 전 백업, Unity의 Visible Meta Files·Force Text 설정, GitHub Desktop 설치와 로그인, 저장소 도입 과정을 담은 운영 기록이다.
- Remote 상시 PC 방식은 제외하고 GitHub/Codex 기반 작업 흐름을 선택한 기록으로 보존한다.
- 게임 기능 구현의 최신 상태를 판정하는 채팅으로 사용하지 않는다.

### 브랜치 · 리모트 활용 비교

- `main`을 안정 브랜치로 두고 별도 작업 브랜치에서 구현·검토·Unity 검증 후 병합하는 운영 흐름을 정립한 채팅이다.
- 개발 순서가 일부 재정리되었지만 실제 구현 상태는 저장소 코드로 판정한다.
- 앞으로는 Git 운용 참고 기록으로만 사용한다.

## 3. 현재 실제 구현 상태

### 완료

1. 타운 기본 레이아웃과 메뉴 전환
   - `TownMenuController`
   - 전투 / 캐릭터 / 상점 / 연구 / 창고 / 옵션 패널 참조 연결
   - 선택한 패널 하나만 활성화하는 `ShowPanel` 구조
   - 사용자가 Unity에서 정상 작동을 확인함

### 구현되었으나 아직 완료 판정 불가

2. 캐릭터 능력치 시스템
   - `StatGrowth`: 1레벨 값 + 레벨당 성장량 계산
   - `CharacterStatsData`: 캐릭터별 ScriptableObject 정의 데이터
   - `CharacterStats`: 현재 레벨에서 정의 스탯 조회
   - `MayhemStats.asset`: 메이헴 데이터 에셋
   - `Dev_Combat`와 `Town` 씬의 `CharacterStats`에 `MayhemStats.asset` 연결

현재 구조는 아래 첫 구간까지만 구현되어 있다.

`ScriptableObject 기본 정의 → 레벨 성장값 조회`

아직 필요한 구간:

`기본 정의 → 현재 레벨 스탯 → Modifier 적용 → 최종 스탯 → 현재 HP/MP 등 런타임 자원`

### 미구현

3. 창고 시스템
4. 대장간 시스템
5. 독립 장비 인스턴스와 장착 시스템
6. 세트 효과와 장비 파생 능력치

현재 저장소에는 이들을 담당하는 정식 `Inventory`, `Storage`, `Forge`, `Equipment` 구현이 없다.

## 4. 능력치 시스템 완료 조건

창고로 넘어가기 전에 다음을 만족해야 한다.

1. 정의 데이터와 런타임 상태 분리
   - `CharacterStatsData`는 변하지 않는 기본 정의로만 사용
   - 레벨, 현재 HP/MP, 장비, 버프 상태는 별도 런타임 데이터로 관리

2. 스탯 계산 계층 분리
   - 기본 스탯
   - 현재 레벨 스탯
   - 장비·버프 Modifier
   - 최종 스탯

3. 재계산 진입점 마련
   - 레벨 변경
   - 장비 장착/해제
   - 버프/디버프 변경
   - 위 사건이 발생할 때만 필요한 값을 재계산

4. 검증 가능한 출력
   - 메이헴 레벨 1 값 확인
   - 메이헴 레벨 50 값 확인
   - 테스트 Modifier 적용 전후 값 확인
   - 장비가 없어도 계산 계층이 독립적으로 작동

5. 현재 확인이 필요한 데이터
   - `MayhemStats.asset`에는 공격속도·이동속도·회복률 등의 구현값이 있으나 `Docs/02_StatsAndDamage.md`의 메이헴 표에는 일부가 없다. 구현값을 자동으로 확정 설정으로 승격하지 않는다.
   - `CharacterStatsData`에는 `cooldownReduction`이 있으나 현재 저장된 `MayhemStats.asset` YAML에는 해당 항목이 보이지 않는다. Unity에서 에셋 검증·재저장 여부를 확인한다.
   - 스탯 소수점과 최종 반올림 규칙은 미확정 상태를 유지한다.

## 5. 확정 개발 순서

1. 타운 기본 레이아웃 / 메뉴 전환 — 완료
2. 캐릭터 능력치 시스템 — 현재 재개 지점
3. 창고 시스템
4. 대장간 시스템
5. 장비 시스템
6. 세트 효과 및 장비 파생 능력치

이 순서는 아래 세로 슬라이스를 완성하기 위한 의존 순서다.

`메이헴 기본 능력치 → 소재 보유 → 제작으로 소재 소비 → 독립 장비 인스턴스 생성 → 창고 확인 → 장착 → 최종 능력치 변화`

## 6. 각 단계의 최소 구현 범위

### 능력치

- 정적 정의와 런타임 상태 분리
- 레벨 성장 계산
- Modifier 적용
- 최종 스탯 조회
- 변경 통지 또는 명시적 재계산 진입점

### 창고

- 소재: 아이템 ID와 수량
- 장비: 독립 인스턴스 목록
- 테스트 소재: 철광석
- 저장 데이터에 포함 가능한 순수 런타임 구조

### 대장간

- 제작법 정의
- 보유 소재 검사
- 소재 소비
- 장비 인스턴스 한 개 생성
- 생성 결과를 창고에 추가
- 실패 시 소재만 소비되거나 장비만 생기는 중간 상태 방지

### 장비

- 장비 정의 데이터와 장비 인스턴스 분리
- 인스턴스별 고유 ID
- 강화 상태
- 추가 옵션 목록과 개별 수치
- 세트 옵션 지정 정보
- 장착 슬롯은 장비 정의가 아니라 특정 인스턴스를 가리킴

### 세트 효과

- 현재 장착된 장비 인스턴스 기준으로 집계
- 장비 변경 시 재계산
- 프레임마다 계산하지 않음
- 고정 장비에 세트를 종속시키지 않고, 소비를 통해 세트 옵션을 부여하는 현재 기획을 보존

## 7. 핵심 결함 방지 규칙

- 동일한 장비 정의로 장비를 여러 개 만들어도 각 장비는 별도 인스턴스다.
- 장비 인스턴스는 서로 다른 고유 ID·강화·옵션·세트 상태를 가진다.
- ScriptableObject 에셋을 개별 장비나 저장 데이터로 직접 변경하지 않는다.
- 장착·제작·저장은 장비 인스턴스 ID를 기준으로 연결한다.
- 구 프로토타입의 `EquipmentManager`, `ForgeManager` 구조를 직접 이식하지 않는다.

## 8. 다음 작업 단위

다음 구현 작업은 **능력치 런타임 계산 기반 완성**으로 고정한다.

권장 작업 브랜치 이름:

`feature/stat-runtime-foundation`

이 작업에서 다룰 범위:

- 현재 `CharacterStats`·`CharacterStatsData`·`StatGrowth` 검토
- 기본/레벨/최종 스탯 계층 정의
- 장비와 버프가 나중에 같은 Modifier 경로를 사용할 수 있도록 최소 구조 마련
- 현재 HP/MP 등 런타임 자원과 정의 데이터 분리
- 메이헴 Lv.1/Lv.50 및 테스트 Modifier 검증 수단 마련

이 작업에서 다루지 않을 범위:

- 창고 UI
- 실제 장비 제작
- 장비 옵션 랜덤 수치 확정
- 세트 효과 비용·수치 확정
- 피해식 미확정 항목의 임의 보완

## 9. 채팅 운영 전환

- 기존 세 채팅은 기록용으로 남기고 더 이상 구현을 이어가지 않는다.
- 새 채팅 하나를 `슬레이어즈 구현 01 - 능력치·장비 세로 슬라이스`로 만든다.
- 새 채팅의 시작 기준은 이 문서와 GitHub `main`이다.
- 첫 요청은 능력치 시스템의 현재 코드 검토와 `feature/stat-runtime-foundation` 작업 계획으로 제한한다.
- 첫 기능 브랜치가 정상 병합된 뒤 기존 세 채팅은 삭제 또는 보관 판정을 할 수 있다.
